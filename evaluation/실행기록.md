# Google Work Agent — 결함과 규칙의 역사적 대응표

조사일: 2026-09-11 (Asia/Seoul)  |  저장소: `solar-ai-dev/google-work-agent`
검토한 마지막 원격 HEAD: `1a0852afd5d1df7ac47b3505cece8068a87403f4` (`codex/issue-251-connected-contract`). 이 SHA는 조사한 소스의 식별자이지 작업 환경을 과거 버전으로 고정하라는 지시가 아니다.

## 범위와 판정

- #210~#283의 74개 이슈 본문과 해당 역사 보고 댓글, `evaluation/results/`의 20개 문서, `evaluation/실행기록.md` 전체를 대조했다. 실행기록에는 별도 Local Node 온도 비교 36회와 더 오래된 합성 READ 49회도 포함된다.
- 자료에 기록된 실제 Run, 직접 Node 검사, 통제 production Graph, 정적 코드 반례를 구분했다. 이 보고서 작성 중 앱·DB·LangSmith 원본을 새로 실행/독립 조회한 것은 아니다.
- 동일 Run을 여러 이슈가 인용하면 새 실행으로 세지 않았다. 실행 계획·수용 조건만 있는 이슈를 실제 실패/성공의 증거로 쓰지 않았다.
- “규칙이 있는 시점에 실패”와 “그 규칙 때문에 실패”는 다르다. 코드·재현 기록으로 확인된 연결, 관측 현상, 원인 미확정을 각 행에 표시했다.
- READ 결함에는 READ의 해석·Query·관측·답변 규칙만 연결한다. 별도 WRITE 표의 승인·실행 규칙을 READ 실패의 원인으로 연결하지 않는다.
- 정확한 target/변경 내용의 Preview + WAITING_APPROVAL은 승인 전 작업 성공으로 인정한다. 틀린 Preview, 허위 완료, tester의 사후 Cancel은 업무 성공으로 바꾸지 않는다.

## 9. 기록 제한과 해석 정정

- #225~#232, #233, #238 및 후행 기능 이슈는 동일 실행을 여러 관점에서 인용한다. 이슈 수를 Run 수로 환산하지 않았다.
- e212ad00의 최초 실행기록에는 READ0과 이에 따른 부분 실패 판정이 있었지만, 후속 #251은 실제 Draft/Task 조회 근거를 회수했다고 기록한다. 원기록을 지우지 않고 정정과 함께 읽었다. 조회 budget0만으로 물리적 READ0을 확정하지 않는다.
- 일부 과거 실행기록의 Run 식별자와 #251 후속 export 표의 Domain Run 식별자가 다르다. 완전한 원천 결속이 없는 부분은 동일 사례·제품 비교만 하고 ID를 임의로 합치거나 서로의 원문을 복원한 것으로 주장하지 않았다.
- f9f1aca7의 대규모 통제 PASS는 당시 실행 보고다. 최종 PASS DB/JUnit·LangSmith가 미회수됐다는 후속 조사도 함께 보존했다. pytest 임시 실패DB7개는 그 원인 자료이지 PASS7개가 아니다.
- 원래 가장 이른 기존 Draft UPDATE 성공에는 정확한 SHA/Run을 회수하지 못한 사용자 회상도 포함된다. 이를 임의의 golden SHA에 결속하지 않았다.
- c30b6887/49e03a5a의 코드 변경 및 34150a26의12Prompt변경을 62fde366에서 측정한13 Run의 입력으로 소급하지 않았다. 검사 소스 추가만으로 새 제품의 Live 개선을 선언하지 않았다.

## 결론

직접 연결이 가장 분명한 악화는 (1) RU 의미의 중복 생성·일치 계약, (2) 두 route에서 합성되지 않은 보호 literal을 객체 동등성으로 거절한 공통 회귀, (3) 생성 schema와 실제 실행 consumer의 불일치다. 반대로 target/ref/capability 검증, 원본 필드 보존, 필요한 Confirmation 연결은 실제 성공과 함께 존재한다. 자료 미발견·Evidence 축소·모델 의미 오해처럼 첫 원천이 없는 실패는 어느 규칙 탓인지 미확정으로 남겼다.

이 문서는 역사 대조 결과이며 규칙 삭제/추가·브랜치 변경·새 실험의 실행 지시가 아니다.
