# 전체본 검수 보정 · Notion 게시 기준

수정일: 2026-09-06  
문서 역할: 문서 보정의 출처·변경 범위·검증 한계와 게시 기준 기록. 기능·정책·기술 계약의 별도 authority가 아니다.

## 1. 기준 자료와 후속 변경

최초 편집은 사용자 제공 `docs.zip` 48개 파일을 기준으로 했다. 원본 ZIP과 최초 Product 기준 `7120df546dc94afdf9e0e3e25a48469ea836095f`는 동일하지 않았다. ZIP에는 일부 기술 문서와 0021 migration의 로컬 선행 변경이 포함되어 있었다.

최초 문서 commit은 `53dd9c8ca7c57d410991adf6bc12d12808d87a59`이며 PR 185의 실제 merge commit은 `7326f2e6c8abcf4269bb226a2de59df07a8a6247`이다. 이전 게시 보고의 `9e0b0c17b63f3711897f577763161f656603efa1a` 표기는 잘못된 추적정보이므로 정정한다.

이번 보정은 로컬 원본·전체 수정본·게시 묶음·재검수 보고를 함께 사용한다. Product의 후속 기준 `671360c112531c5aa2242c82d5f20418d00da34a`에 들어온 변경을 먼저 대조했다. 해당 기준의 전체 docs는 로컬 전체본과 원격 변경분으로 구성하고 Git blob hash로 대조한다. 편집·의미 검수는 로컬 전체 문서에서 수행하며 원격 API의 일부 발췌만으로 전체 검수를 대신하지 않는다.

후속 코드가 기술 문서를 변경한 사실과 이번 문서 보정의 변경 범위는 다르다. 기존 기술 변경·0021/0022·제품 코드를 되돌리거나 ZIP으로 통째로 덮어쓰지 않는다.

## 2. 최소 보정 내역

|---|---|---|
| PRD | 같은 요청의 재전송이라는 표현이 네트워크 재시도와 새 제출을 혼합 | 동일 identity·동일 입력의 재시도와 종료 후 새 요청을 구분 |

기존 요구사항·기능·정책 ID를 재번호하지 않는다. 기능 번호와 정책 번호를 연결하는 새 의존 체인, 문서 버전의 연쇄 갱신 규칙을 만들지 않는다. 문서 현재성은 수정일로 표시하고 실행 schema·wire version은 보존한다.

## 3. 변경하지 않는 기술 계약과 검증 한계

기술 Canonical, Repository Architecture, Domain 상태 전이, SQL, 제품 코드, enforcement는 이번 보정의 수정 대상이 아니다. 다음은 별도 담당의 정합화·구현 검증 대상으로 남긴다.

- 최신 Domain·DB에 local-workspace actor와 0022 migration이 추가됐다. 이전 ZIP의 Google Account 필수 FK 간극을 계속 계약 부재로 보고하지 않는다. 기존 데이터 migration·계정 격리·실행 중 만료의 실제 검증은 별개다. 남아 있는 과거 ERD·설명까지 모두 정합화됐다고 간주하지 않는다.
- 기본 GitHub Repository의 SETTINGS_DEFAULT와 immutable Run binding은 업로드 문서에도 있었고 최신 Product에도 반영됐다. 계약 존재와 실제 Settings/권한 변경/override E2E를 구분한다.
- 개발 전용 optional OAuth secret 예외는 정책·보안·인프라·테스트 문서상 일치한다. Signed 배포의 예외로 확대하지 않으며 실제 저장·redaction·배포 검증은 별도로 확인한다.
- 새 Header UX와 보호 테스트의 기존 중앙 Google chip·계정 표시 요구는 후속 검증 계약에서 정리해야 한다.
- Activity의 기존 실행 식별자와 상태 이력은 재사용 후보다. process-local SSE와 최신 Snapshot만으로 과거 모든 상세가 복원된다고 단정하지 않는다. 추가 LLM 호출 없이 이력·결과 조회를 연결하는 검증은 7.5 범위다.
- database/README의 fresh-install 안내와 forward/adoption migration 적용 순서를 별도로 확인한다. 기존 migration을 재번호하거나 실행해 문서 보정을 대신하지 않는다.
- 보호 문서의 표 안 비escape pipe 등 기존 표시 문제는 원본 의미를 변경하지 않고 게시 형식 변환에서 구분한다. 형식 검사와 기술 계약의 정확성 검증을 혼동하지 않는다.

문서 검수는 제품 실행·실제 Connector E2E·릴리스 검증을 수행한 것이 아니다. 기존 알려진 실패를 문서 변경만으로 종료하거나 실제 사용자 요청의 성공으로 보고하지 않는다.

## 4. Notion 정보 구조와 게시 순서

루트 이름은 `MCP-Work-Agent`다. 현행 주요 문서는 번호순으로 바로 나열하고 변경 이력·선택 이유·작업 현황·과거 안내·기타 참고는 `90 변경 이력 / 선택 이유 / 참고 자료`에 둔다.

단일 원문은 페이지를 열면 요약과 원문 전체가 바로 보인다. 실제 독립 원문이 여러 개인 주제만 하위 문서를 나열한다. PRD와 요구사항이 하나의 원문이면 별도 사본 두 개로 만들지 않는다. 탐색용 번호는 GitHub 파일명이나 원문 ID를 변경하는 기준이 아니다.

게시 순서는 GitHub 보정 확정 → Notion 구조 배치 → 선정 원문 전체 게시 → 같은 페이지 상단 요약 추가 → 구조·본문 재조회 검증이다. 기존 페이지 ID와 하위 페이지를 가능한 한 재사용하며 무단 삭제하지 않는다.

요약은 게시된 원문만 근거로 작성한다. 새로운 요구사항을 넣거나 원문의 정합화 대기를 몰래 해결하지 않는다. 요구사항을 구현 완료로, 코드 존재를 E2E 통과로 표현하지 않는다. 보호 원문의 간극은 원문 밖의 안내로 구분한다.

원문 수정일과 단순 게시일을 혼동하지 않는다. Notion 게시 작업은 여러 호출로 나뉠 수 있으며 API 성공을 전체 페이지 게시·검증 완료로 보고하지 않는다. 최종 URL·본문·부모 관계·요약과 원문의 일치 결과는 별도 게시 결과로 기록한다.
